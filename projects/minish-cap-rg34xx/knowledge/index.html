01 / PHILOSOPHY

Minimal intervention, visible knowledge

↑ Index

Preservation, containment, focus, restoration and minimalism are engineering constraints here, not branding. The original experience remains the reference while platform work is kept as small and inspectable as practical.

Preserve identity

Art, music, SFX, UI, cadence and control identity remain authoritative. A port can improve infrastructure without visually rewriting the game.

Contain the change

Fix the demonstrated problem inside the smallest useful boundary. Do not turn every timing, build or audio issue into a whole-engine redesign.

Explain more than you change

Minimalism applies to intervention, not documentation. A small patch can deserve a detailed account of evidence, alternatives and limitations.

02 / TIMING

A 120 Hz panel is not 120 FPS game logic

↑ Index

The high-refresh investigation separated logical cadence, explicit presentation calls and panel refresh. The retained direction kept game logic around 59.7275 Hz, used the panel around 119.455 Hz, and adopted one explicit presentation per logical tick.

In the recorded comparison, tick-lateness p95 moved from approximately 5.791 ms to 0.028 ms under the tested conditions.

The important lesson is not the marketing number. It is that instrumentation was allowed to reject the original hypothesis and preserve the original game cadence while improving presentation behaviour.

03 / AUDIO

Measure timing, then listen

↑ Index

Audio work on Cortex-A53/H700 combined callback/timing evidence with human listening. Later retained configuration evidence uses audio 1600; the project record discusses a nominal interval change from roughly 40 ms to 33.333 ms.

A remaining callback-gap/outlier warning was kept in the record rather than hidden.

Reusable lesson: a heuristic underrun/callback counter is not a literal count of audible defects. Instrumentation and listening answer different questions.

04 / BENCHMARKING

Validate the context before the number

↑ Index

Early AutoLab measurements taken through direct SSH were rejected because frontend/background state did not represent a normal Ports launch.

The improved method used a normal Ports-session context, deterministic replay and CPU/GPU restoration between variants.

Reusable lesson: before optimising a benchmark, prove that its environment represents how the software is actually used.

05 / NEGATIVE RESULTS

Rejected experiments remain useful

↑ Index

GPU backend

An experimental GPU renderer failed and was not promoted. It remains useful as a warning against blindly retrying a plausible idea after context loss.

Fullscreen clear

A fullscreen-clear experiment existed but was not adopted into the retained V1 line.

Mixed optimisation data

The record keeps unfavourable observations too, including higher maximum temperature in one comparison and slightly higher RSS.

06 / PUBLICATION

Publication failures are engineering lessons too

↑ Index

The first public Minish Cap publication correctly excluded private/proprietary material but also hid too much safe engineering context. The correction is explicit: sanitise what cannot be shared; publish the reasoning that can.

Later site work added further reusable lessons: local QA is not the same as production deployment; existing artifacts should be checked before asking the operator to recreate them; and automation should be smaller than the problem it is meant to solve.

Reusable lesson: minimal public risk does not require minimal public knowledge.
