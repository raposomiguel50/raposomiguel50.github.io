The Minish Cap - RG34XX

An unofficial RG34XX/H700 integration of Project Picori, developed with the ANBERNIC RG34XX-H and muOS as the validated reference configuration.

I chose the RG34XX-H because its horizontal form and design closely recall the original Game Boy Advance. The GBA was the first console I owned, given to me by my father after growing up mainly with PCs and PC games.

01 / OVERVIEW

Why the RG34XX-H and why native

↑ Index

Personal connection

I grew up mainly with PCs and PC games. The Game Boy Advance was the first console I owned, given to me by my father. The RG34XX-H is, for me, the modern handheld that most closely recalls the GBA as a physical device.

Technical fit

Its 720x480 display allows the GBA's original 240x160 image to scale exactly at 3x without changing its proportions. The H700 and muOS also provide a useful constrained ARM/Linux target for native-port work.

Native execution

Running the project natively removes the GBA emulation layer. The game executes as AArch64 software within Linux/muOS, giving the port more direct control over timing, presentation, audio, threading, input and lifecycle behaviour.

Creative headroom

The additional hardware margin makes it possible to imagine and explore what the original developers could have achieved with more optimisation time and more room in the hardware to express their vision and creativity.

Project Picori foundation

The integration is based on Project Picori revision e72663ca4059dabf9dbf7f03c36fc791d90b8db5. The public repository contains the H700 integration layer rather than duplicating the complete upstream tree.

02 / PHILOSOPHY

Preservation-led engineering

↑ Index

The project uses preservation, containment, focus, restoration and minimalism to guide platform-specific changes.

Preservation

The original game remains the reference for art, music, sound effects, interface, cadence and control identity.

Containment

Build, timing, audio and lifecycle changes are kept within the smallest practical boundary that addresses the observed issue.

Focus

Stable scope is kept separate from optional research such as remastering or alternate rendering paths.

Restoration

Platform adaptation aims to retain the original behaviour and presentation rather than replace them with a different interpretation.

Minimalism

Technical interventions are kept as small as practical, while documentation remains detailed enough to support review and reuse.

Priorities

Changes are selected according to project purpose, target constraints and evidence rather than feature count or technical novelty alone.

04 / VALIDATION

Measured results and limits

↑ Index

Retained private V1 SHA-256:

787ba3cb8c297ea44a0605745347fe5a6e792094f0be755b51a8200c1eadc710

Timing

Accepted direction: logic ~59.7275 Hz, panel ~119.455 Hz, one explicit presentation per logical tick. A recorded comparison improved tick-lateness p95 from ~5.791 ms to ~0.028 ms.

Runtime evidence

Later retained configuration evidence includes CPU 936 MHz, GPU 420 MHz, audio 1600 and TMC_RENDER_THREADS=3.

Evidence boundaries

The record keeps display refresh, CPU frequency, compatibility and reproducibility claims separate from measurements that do not directly establish them.

05 / PUBLICATION

Public and private boundaries

↑ Index

Published

Source patches, launcher/runtime integration material, reference hashes, philosophy, knowledge base, patch map, validation, reconstruction status and development method.

Not published

No GBA ROM, extracted Nintendo assets, saves, private builds, device backups or validated V1 executable are included.

VirtuaAPU boundary

The private V1 used VirtuaAPU. The audited revision had no explicit published licence file, so its source and the executable incorporating it are not redistributed.
